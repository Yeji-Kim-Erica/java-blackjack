- 변경 범위가 넓거나 좁다고 판단한 이유를 분석하여 작성해 주세요.
  변경 범위가 매우 넓다고 판단합니다.
  '베팅 금액'이라는 하나의 도메인 개념이 추가되었을 뿐인데,
  도메인(Player, Game), UI(InputView, OutputView), 컨트롤러(BlackJackController),
  그리고 데이터를 전달하는 DTO까지 거의 모든 계층에 동시다발적인 수정이 발생하고 있기 때문입니다.
  특히 Game 클래스에 수정이 집중되는 것을 통해, Game이 게임 로직 수행, 수익 계산, 흐름 제어, DTO 변환 등 너무 많은 책임을 짊어지고 있음을 알 수 있습니다.
  이로 인해 도메인의 응집도는 낮아지고 각 계층 간의 결합도는 높아져, 단일 요구사항 추가에도 연쇄적인 코드 변경과 테스트 코드 수정이 강제되는 넓은 변경 범위를 가지게 되었습니다.

- 현재 구조에 대한 유지 또는 보완 판단과 그 근거를 작성해 주세요.
  현재 구조는 유지하기 어려우며, 보완이 필수적이라고 판단합니다.
    - 오버 엔지니어링으로 인한 계층 간 경계 모호성 해소:
      현재 Delegate 패턴 등이 얽혀 있어 컨트롤러와 도메인(Game)의 흐름 제어 역할이 혼재되어 있습니다.
      순차적 로직에 맞는 직관적인 MVC 구조로 컨트롤러와 도메인의 강한 결합을 끊어내야 한다고 생각합니다.
    - 도메인 객체의 책임 분리:
      Game 클래스가 도맡고 있는 기능들을 분산시켜야 합니다.
      예를 들어, 베팅 금액과 수익 계산을 담당하는 별도의 도메인 객체를 분리해 각각 메인 기능을 책임지도록 자율성을 높여야 한다고 생각합니다.
    - 개방-폐쇄 원칙을 준수하도록 구조 개선:
      새로운 기능이 추가될 때 기존 코드의 수정을 최소화하려면,
      도메인의 비즈니스 로직이 UI나 흐름 제어 로직에 의존하지 않도록 단방향 의존성을 확립해야 합니다.
      DTO의 활용성을 더 높여 레이어 간의 단절을 확실히 구현할 계획입니다.

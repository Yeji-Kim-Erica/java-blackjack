# 사이클1: 사전학습

## 실험 범위
- 규칙: Ace의 1/11 처리
- 설명: 합계에 따라 1 또는 11로 계산
- 적정 크기: 메서드 1-2개

## 실험1: main 기반 검증의 한계

### 해볼 것
1. 선택한 규칙을 main 메서드에서 구현
2. 테스트 케이스 3개로 실행해본다
3. 케이스를 6개로 늘려본다

### 관찰할 것
- **케이스가 늘어나니 어디를 수정해야 했는가?**
  - **사실**: 테스트 케이스 코드 중 테스트할 입력값과 기대 결과값을 제외하고 나머지 코드가 동일한데 매번 복붙해서 사용해야 했다.
  - **문제**: 테스트 케이스가 3개일 때는 동작 결과가 한눈에 알아보기 쉬웠지만, 6개가 되니 출력문이 6개가 맞는지 세어서 확인해야 했다.  
  

- **수정하면서 놓친 것은 없는가?**
  - **사실**: 이전 코드를 덩어리째 복사해서 새로운 케이스를 만들 때, 입력값은 수정해놓고 기대 결괏값을 상황에 맞게 변경하는 것을 까먹지 않기 위해 계속 신경 써야 했다.  
  - **문제**: 수동으로 코드를 복사해서 쓰다 보니, 매번 의식적으로 변수 하나하나를 확인하지 않으면 잘못된 기댓값을 검증하는 테스트를 만들 위험이 있었다.  
  

- **이전 케이스가 여전히 동작하는지 어떻게 확인했는가?**
  - **사실**: printf 출력 양식을 추가해서 케이스별 시행 결과를 바로 확인할 수 있게 했다.  
  - **문제**: 같은 내용의 코드를 케이스 중간마다 일일이 붙여넣는 과정에서 일부 케이스에 해당 코드를 빼먹지는 않았는지 체크해야 했다.  

## 실험2: 테스트 코드 작성

### 해볼 것
1. 같은 로직을 JUnit 테스트로 작성 (최소 3개)
2. 경계 케이스나 예외 케이스 1개 추가
3. 테스트 작성이 어려운 부분을 표시

### 관찰할 것
- **테스트를 작성하기 어려운 코드가 있는가?**    
  Ace의 값을 결정하는 핵심 로직이 들어간 Application의 determineAce 메서드의 테스트를 작성하기 어려웠다.


- **어렵다면, 무엇 때문에 어려운가?**    
  public으로 설정된 main 메서드에 determineAce 메서드에 변수로 넘겨줄 인자가 하드코딩되어 있어서 변수에 대한 외부에서의 접근이 어려웠다.
  이를 해결하기 위해 임시방편으로 Application의 determineAce 메서드 공개 범위를 default로 변경했다.


- **테스트를 쉽게 하려면 코드를 어떻게 바꾸고 싶은가?**  
  로직 부분과 테스트 케이스 코드를 클래스 단위로 분리하고 싶다.  
  테스트 케이스는 test 패키지의 하위 클래스들에서 다루게 하고,
  로직 관련 코드는 Application의 main 메서드에서 또는 Ace 관련 로직을 모아두는 Ace 클래스를 만들어 다루고 싶다.  


- **테스트가 어려웠던 코드 1곳:**  
  ```java
    private static int determineAce(List<Integer> cards) {
        int sum = sum(cards);
        if (isBust(sum + MAX_ACE)) {
            return MIN_ACE;
        }
        return MAX_ACE;
    }
  ```
  

- **바꾸고 싶은 부분과 이유**  
  - determineAce 메서드의 접근 제한자를 private에서 default 또는 public으로 변경하고 싶다.
    test 패키지에서도 해당 메서드를 사용해 테스트해보기 위해서다.
  - Ace의 1/11 판정 로직을 점수 계산을 담당하는 클래스를 따로 두어 관리하고 싶다.
    테스트 케이스 및 게임 실행, 판정 로직이 섞인 지금은 책임 분리가 적절히 되지 않은 상태로 느껴지기 때문이다.
  

## 산출물
- **테스트 단위에 대한 내 의견**  
  핵심 로직을 다루는 메서드 단위로 테스트가 이루어져야 한다고 생각한다.


- **반드시 테스트할 것 1개 / 하지 않을 것 1개**  
  - **반드시 테스트할 것**: 기능이 정상 작동하는 데 중대한 영향을 미치는 핵심 로직 메서드
  - **테스트하지 않을 것**: 메인 로직을 구성하는 세부 로직에 관한 private 메서드

## 이번 사이클에서 답할 질문
- **애플리케이션을 직접 실행해서 검증하는 것으로 충분한가?**  
  애플리케이션을 직접 실행해서 검증하게 되면 전체적인 흐름은 검증 가능하지만,
  특정 로직을 분리해 해당 기능이 정상적으로 작동하는지 확인하기 어렵다. 따라서 부족하다.


- **테스트를 통해 어디까지 검증할 것인가?**
  메인 기능과 그를 구성하는 핵심 로직이 담긴 메서드를 최소 테스트 단위로 두고 검증한다.


- **테스트를 하기 어려운 코드는 무엇인가?**
  파라미터나 직접 입력 형식이 아닌 하드코딩으로 변수를 대입해 자유로운 케이스 적용이 어려운 코드이다.


- **무엇을 테스트하고 무엇을 버릴 것인가?**
  기능이 정상 작동하는 데 중대한 영향을 미치는 핵심 로직 메서드를 테스트하고,
  메인 로직을 구성하는 세부 로직에 관한 private 메서드는 버린다.

# 사이클 1: 토론 활동

## 산출물
**그룹 규칙**
(If-Then) 만약 메서드에 public/protected/package 접근제어자가 보이면
→ 정상 케이스와 예외 케이스를 각각 별개의 단위 테스트로 작성한다

(If-Then) 만약 도메인 로직에서 Random 호출이 보이면
→ 호출을 바깥으로 이동하고 값을 외부에서 주입받도록 변경한다

(If-Then) 만약 private 메서드인데 테스트가 필요하다고 판단되면
→ 해당 메서드를 별도의 클래스로 분리한다

(우선순위) 리팩터링 순서
1) 테스트가 필요한 private 메서드를 외부 클래스로 분리
2) 내부 랜덤성을 외부 주입으로 변경

(금지) private 메서드, Main 메서드, parseXxx() 등 Java 기본 제공 메서드,
타입 범위 초과 여부, 입출력, 랜덤은 테스트하지 않는다
(대신 public으로 드러난 순수 도메인 로직만 테스트한다)

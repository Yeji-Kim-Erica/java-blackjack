# java-blackjack

블랙잭 미션 저장소

# 사이클1: 사전학습

## 실험 범위

- 규칙: Ace의 1/11 처리
- 설명: 합계에 따라 1 또는 11로 계산
- 적정 크기: 메서드 1-2개

## 실험1: main 기반 검증의 한계

### 해볼 것

1. 선택한 규칙을 main 메서드에서 구현
2. 테스트 케이스 3개로 실행해본다
3. 케이스를 6개로 늘려본다

### 관찰할 것

- **케이스가 늘어나니 어디를 수정해야 했는가?**
    - **사실**: 테스트 케이스 코드 중 테스트할 입력값과 기대 결과값을 제외하고 나머지 코드가 동일한데 매번 복붙해서 사용해야 했다.
    - **문제**: 테스트 케이스가 3개일 때는 동작 결과가 한눈에 알아보기 쉬웠지만, 6개가 되니 출력문이 6개가 맞는지 세어서 확인해야 했다.


- **수정하면서 놓친 것은 없는가?**
    - **사실**: 이전 코드를 덩어리째 복사해서 새로운 케이스를 만들 때, 입력값은 수정해놓고 기대 결괏값을 상황에 맞게 변경하는 것을 까먹지 않기 위해 계속 신경 써야 했다.
    - **문제**: 수동으로 코드를 복사해서 쓰다 보니, 매번 의식적으로 변수 하나하나를 확인하지 않으면 잘못된 기댓값을 검증하는 테스트를 만들 위험이 있었다.


- **이전 케이스가 여전히 동작하는지 어떻게 확인했는가?**
    - **사실**: printf 출력 양식을 추가해서 케이스별 시행 결과를 바로 확인할 수 있게 했다.
    - **문제**: 같은 내용의 코드를 케이스 중간마다 일일이 붙여넣는 과정에서 일부 케이스에 해당 코드를 빼먹지는 않았는지 체크해야 했다.

## 실험2: 테스트 코드 작성

### 해볼 것

1. 같은 로직을 JUnit 테스트로 작성 (최소 3개)
2. 경계 케이스나 예외 케이스 1개 추가
3. 테스트 작성이 어려운 부분을 표시

### 관찰할 것

- **테스트를 작성하기 어려운 코드가 있는가?**        
  Ace의 값을 결정하는 핵심 로직이 들어간 Application의 determineAce 메서드의 테스트를 작성하기 어려웠다.


- **어렵다면, 무엇 때문에 어려운가?**    
  public으로 설정된 main 메서드에 determineAce 메서드에 변수로 넘겨줄 인자가 하드코딩되어 있어서 변수에 대한 외부에서의 접근이 어려웠다.    
  이를 해결하기 위해 임시방편으로 Application의 determineAce 메서드 공개 범위를 default로 변경했다.


- **테스트를 쉽게 하려면 코드를 어떻게 바꾸고 싶은가?**      
  로직 부분과 테스트 케이스 코드를 클래스 단위로 분리하고 싶다.      
  테스트 케이스는 test 패키지의 하위 클래스들에서 다루게 하고,    
  로직 관련 코드는 Application의 main 메서드에서 또는 Ace 관련 로직을 모아두는 Ace 클래스를 만들어 다루고 싶다.


- **테스트가 어려웠던 코드 1곳:**
  ```java
    private static int determineAce(List<Integer> cards) {
        int sum = sum(cards);
        if (isBust(sum + MAX_ACE)) {
            return MIN_ACE;
        }
        return MAX_ACE;
    }
  ```


- **바꾸고 싶은 부분과 이유**
    - determineAce 메서드의 접근 제한자를 private에서 default 또는 public으로 변경하고 싶다.    
      test 패키지에서도 해당 메서드를 사용해 테스트해보기 위해서다.
    - Ace의 1/11 판정 로직을 점수 계산을 담당하는 클래스를 따로 두어 관리하고 싶다.    
      테스트 케이스 및 게임 실행, 판정 로직이 섞인 지금은 책임 분리가 적절히 되지 않은 상태로 느껴지기 때문이다.

## 산출물

- **테스트 단위에 대한 내 의견**  
  핵심 로직을 다루는 메서드 단위로 테스트가 이루어져야 한다고 생각한다.


- **반드시 테스트할 것 1개 / 하지 않을 것 1개**
    - **반드시 테스트할 것**: 기능이 정상 작동하는 데 중대한 영향을 미치는 핵심 로직 메서드
    - **테스트하지 않을 것**: 메인 로직을 구성하는 세부 로직에 관한 private 메서드

## 이번 사이클에서 답할 질문

- **애플리케이션을 직접 실행해서 검증하는 것으로 충분한가?**      
  애플리케이션을 직접 실행해서 검증하게 되면 전체적인 흐름은 검증 가능하지만,    
  특정 로직을 분리해 해당 기능이 정상적으로 작동하는지 확인하기 어렵다. 따라서 부족하다.


- **테스트를 통해 어디까지 검증할 것인가?**    
  메인 기능과 그를 구성하는 핵심 로직이 담긴 메서드를 최소 테스트 단위로 두고 검증한다.


- **테스트를 하기 어려운 코드는 무엇인가?**    
  파라미터나 직접 입력 형식이 아닌 하드코딩으로 변수를 대입해 자유로운 케이스 적용이 어려운 코드이다.


- **무엇을 테스트하고 무엇을 버릴 것인가?**    
  기능이 정상 작동하는 데 중대한 영향을 미치는 핵심 로직 메서드를 테스트하고,    
  메인 로직을 구성하는 세부 로직에 관한 private 메서드는 버린다.

# 사이클 1: 토론 활동

## 그룹 규칙

(If-Then) 만약 메서드에 public/protected/package 접근제어자가 보이면    
→ 정상 케이스와 예외 케이스를 각각 별개의 단위 테스트로 작성한다

(If-Then) 만약 도메인 로직에서 Random 호출이 보이면    
→ 호출을 바깥으로 이동하고 값을 외부에서 주입받도록 변경한다

(If-Then) 만약 private 메서드인데 테스트가 필요하다고 판단되면    
→ 해당 메서드를 별도의 클래스로 분리한다

(우선순위) 리팩터링 순서

1) 테스트가 필요한 private 메서드를 외부 클래스로 분리
2) 내부 랜덤성을 외부 주입으로 변경

(금지) private 메서드, Main 메서드, parseXxx() 등 Java 기본 제공 메서드,    
타입 범위 초과 여부, 입출력, 랜덤은 테스트하지 않는다    
(대신 public으로 드러난 순수 도메인 로직만 테스트한다)

# 사이클 1: 피드백 활동

## 그룹 규칙 업데이트본

### 1. (If-Then) 테스트 및 설계 원칙

- 접근 제어자: 만약 메서드에 public, protected, package 접근제어자가 보이면    
  → 정상 케이스와 예외 케이스를 각각 별개의 단위 테스트로 작성한다.
- 랜덤 로직: 만약 도메인 로직에서 Random 호출이 보이면    
  → 호출을 바깥으로 이동하고 값을 외부에서 주입받도록 변경한다.
- private 테스트: 만약 private 메서드인데 테스트가 필요하다고 판단되면    
  → 해당 메서드를 별도의 클래스로 분리한다.
- 생성 로직: 생성할 때 테스트가 필요한 로직이 있는 경우라면    
  → 정적 팩터리 메서드를 사용하고, 해당 메서드는 반드시 테스트한다.
  > **주의**: 만약 정적 팩터리 메서드를 사용하면서도 "굳이 테스트해야 하나?"라는 의문이 든다면, 오버 엔지니어링임을 고려하여 단순 생성자 사용을 검토한다.

### 2. (금지) 테스트 제외 대상

다음에 해당하는 항목은 테스트하지 않으며, public으로 드러난 순수 도메인 로직만 테스트 대상으로 삼는다.

- 메서드 및 기본 기능: private 메서드, Main 메서드, parseXxx() 등 Java 기본 제공 메서드, Getter 및 Setter.
- 환경 및 데이터: 타입 범위 초과 여부, 입출력(I/O), 랜덤.
- 구조적 요소: 추상 클래스, 인터페이스, 검증할 만한 로직이 내부에 없는 생성자.
- 조립 메서드: public 메서드일지라도 내부 로직이 '다른 단위 테스트에서 이미 검증을 완료한 메서드들'만을 단순히 호출하여 조립하는 경우.

### 3. (우선순위) 리팩터링 순서

코드 구조를 개선할 때는 다음의 우선순위를 준수한다.

- 테스트가 필요한 private 메서드를 외부 클래스로 분리
- 내부 랜덤성을 외부 주입으로 변경

## 사이클 종료 자기 점검

### 1. 테스트 단위를 어떻게 정했는가? 왜?

테스트의 단위는 기능으로 정했습니다.

우리가 실제로 테스트 코드를 작성하게 되는 건 물론 메서드 단위이지만, 이는 설계와 클래스 분리가 적절히 일어났을 때 보이는 코드 상에서의 자연스러운 ‘현상’일뿐, 우리가 기준 규칙으로 참고해야 할 ‘지향점’은
아니라고 생각했습니다. 테스트의 단위를 ‘기능’으로 정하고 테스트를 작성할 때, 테스트의 진짜 목적인 ‘기능의 동작 여부’가 확인 가능해집니다.

사전학습 활동을 진행할 때, 기능을 다룬 메서드를 테스트하려고 시도했는데 해당 메서드가 private으로 테스트가 불가했던 경험이 있습니다.     
이때, 만약 제가 테스트의 단위를 메서드로 정하고, 단순히 ‘public 메서드’만을 테스트 대상으로 생각했다면, 이런 문제 상황을 규칙에 기반해서 해결하기 어려웠을 것이라고 생각합니다.     
당시 이미 ‘기능’을 테스트의 단위로서 바라보고 있었기 때문에 토론 활동에서도 ‘공개 메서드를 테스트하는 것을 기본으로 하되, private 메서드인데 테스트가 필요한 경우는 해당 메서드를 별도의 클래스로
분리하자.’는 의견을 제시할 수 있었습니다.

실제로 해당 규칙이 그룹에게 많은 공감을 받아, 규칙 문서에 내용이 포함되었고, 페어와 블랙잭 미션을 구현하면서 규칙을 적용해볼 수 있는 순간이 많이 있었습니다.

### 2. 테스트가 어려웠던 코드는? 어떻게 해결했는가?

사전활동에서 main 메서드에서 모든 로직을 구현하라는 제약 사항으로 인해 Ace의 1/11 값 판별 로직이 `Application` 클래스에 private 메서드로 구현되었습니다. 해당 기능의 테스트 코드를
작성하는 과정에서 불편을 느꼈고, 클래스 분리를 떠올렸지만, 클래스는 1개만 사용한다, main에서 로직을 구현한다 등의 가이드라인에 충실하기 위해 다른 임시방편을 사용했습니다. private으로 선언되어 있던
`determineAce` 메서드의 접근 제어자를 default로 변경하는 방법을 사용하고, 이때 떠오른 생각을 기록해 토론 활동에서 규칙을 정할 때 근거로 사용했습니다.

페어와 블랙잭 구현 중, Card의 일급 컬렉션 클래스인 `Deck` 클래스에서 점수 합계를 계산하는 과정에서 Ace의 1/11 값을 판별하는 로직이 private 메서드로 포함되어 있었는데, Ace의 1/11
값 판별 로직을 테스트해봐야겠다는 판단(Ace의 1/11 값 판별이 중요 기능 중 하나라는 판단)이 서면서 해당 부분을 `AceScoreDiscriminator` 클래스로 분리해 해당 규칙을 적용시켜보았습니다.

### 3. 처음에 테스트에 대해 어떻게 생각했는가?

평소 테스트해야 하는 메서드의 범위의 기준을 명확히 정하는 것이 어렵다고 느꼈습니다. 처음에는 public 메서드로 선언된 모든 메서드에 테스트 코드를 만들었고, 시간이 지날수록 개인적인 판단을 활용해 ‘굳이
테스트하지 않아도 명확하다’고 생각되는 메서드에 한해서는 테스트 코드를 작성하지 않게 되었습니다.

하지만, 명확한 기준을 정해두지 않고 작업을 진행하자, 어떤 클래스에서는 단순한 로직임에도 테스트 코드가 존재하고 또 다른 클래스에서는 해당 경우 테스트 코드를 작성하지 않는 등 들쭉날쭉한 테스트 코드 작성이
이어졌습니다.

이로 인해 점점 tdd는 실무적인 도움을 위해 활용하는 방법이 아닌, 남에게 ‘나 tdd로 개발해요’를 보여주기 위한 겉핥기식 도구로 전락해갔습니다.

### 4. 지금은 어떻게 생각하는가?

사전학습, 토론, 페어와 규칙을 적용하면서 진행한 블랙잭 구현, 이후 느낀 점에 대한 그룹 토론 및 사례 공유, 규칙 문서 업데이트 등 다양한 활동을 거치면서 점진적으로 테스트 코드에 대한 저만의 규칙과 철학이
생기고 있습니다. 이번 그룹 대화를 통해 진행한 규칙 업데이트에서 ‘로직이 들어가있지 않은 순수한 생성자, getter 메서드는 공개 메서드일지라도 테스트에서 제외한다’ 등등 제외할 경우를 추가하면서, 점점 더
‘기능’ 중심의 테스트가 이루어져야 한다는 가치관이 힘을 얻고 있는 것 같습니다.

### 5. 왜 달라졌는가?

앞선 답변들에서 말씀드렸듯, 실제 미션 진행 과정에서 겪은 시행착오를 통해 테스트 단위에 대한 확실한 개인의 철학이 생기기 시작했기 때문입니다. ‘너무 모호하다’, ‘이걸 정확히 제대로 하는 사람이 많지 않을
거 같다’, ‘나도 할 수 있는 만큼만 해야겠다’는 저의 안일한 생각에 큰 변화가 생긴 것 같습니다.
